01 —

Architecture principles

Multi-tenant by role

Single deployment serving all user types with role-based access control. Not multi-organization — single org, multiple permission levels.

API-first design

All functionality accessible via API. The web interface consumes the same APIs that integrations use. Enables future mobile apps or partner integrations without rebuilding.

Event-driven automation

System events (registration completed, payment received, deadline reached) trigger configurable actions. Replaces the current Zapier layer with native event handling.

Geographic data isolation

Local Coordinators see only their city's data. Teachers see only their trip's data. Admins see everything. Enforced at the data layer, not just the UI.

Offline-resilient integrations

External service failures (Stripe down, QBO unreachable) must not break core platform functionality. Queue failed operations and retry with exponential backoff.

Technology-agnostic

This specification can be implemented on any modern web stack. No framework, language, or hosting provider is prescribed.

Authentication & authorization

Authentication
  • Email + password authentication (bcrypt or argon2 hashing)
  • Magic link option for low-frequency users (travelers, parents, host families)
  • Session-based or JWT token-based (implementation choice)
  • Password reset via email
  • Account lockout after configurable failed attempts
Role-based access control

Host families (own city)————RWRW

R = Read, RW = Read/Write, — = No access. Geographic filtering enforced at database query level for Local Coordinators.

04 —

Integration specifications

Stripe (Payment Processing)

Pattern: Direct API + Webhooks

  • Create Payment Intents (one-time charges: deposits, late fees, event tickets)
  • Create Subscriptions (recurring payment plans)
  • Cancel Subscriptions (on auto-cancellation or manual cancel)
  • Process Refunds (admin-initiated)
  • Handle Webhooks: payment_intent.succeeded, payment_intent.payment_failed, invoice.paid, invoice.payment_failed, customer.subscription.deleted
  • Business rules: auto-assess late fee after grace period, auto-cancel after threshold, configurable CC fee pass-through
  • Error handling: retry per Stripe's built-in schedule, notify admin after final failure, idempotent webhook processing
QuickBooks Online (Accounting)

Pattern: OAuth 2.0 + REST API (scheduled sync)

  • Create Sales Receipts for each payment — individually labeled, not batched
  • Each transaction includes: student name, trip name/ID, payment type, amount, date
  • Map to configurable QBO income accounts
  • Handle credit card fee accounting (expense line item)
  • Sync frequency: configurable (recommended every 4-6 hours)
  • Error handling: queue on API unavailability, retry with backoff, track qbo_synced flag per payment, respect 500 req/min rate limit
HubSpot (CRM & Marketing)

Pattern: OAuth 2.0 + REST API (event-driven + scheduled)

  • Create/update Contacts when students register
  • Sync custom properties: trip name, registration status, payment status, program type
  • Read Contacts from school visit lead lists (for host family recruitment)
  • Direction: Platform → HubSpot (registration events, status changes); HubSpot → Platform (lead data, read-only)
  • Deduplication: match on email address
Asana (Project Management)

Pattern: OAuth 2.0 + REST API (event-driven)

  • Create Project when new trip is created
  • Create Tasks for key milestones (configurable triggers)
  • Create Task Comments from relevant emails (replaces manual copy-paste)
  • Email-to-Asana: platform monitors designated inboxes, matches email to trip based on subject/sender patterns, creates comment with full email content
  • Read Task status from Asana for platform dashboard display
  • Error handling: queue on unavailability, check for existing task before creating (duplicate prevention)
Email Service

Pattern: API-based (SendGrid, Mailgun, AWS SES, or similar)

  • Transactional emails (confirmations, receipts, reminders) + bulk emails (admin/LC to filtered groups)
  • Template system with admin-editable content and variable substitution
  • Variables: {{student_name}}, {{trip_name}}, {{payment_amount}}, {{task_deadline}}, {{event_name}}, {{portal_login_url}}, etc.
  • Delivery tracking (sent, delivered, bounced), unsubscribe handling
Google Calendar

Pattern: iCal feed generation (no OAuth required)

  • Generate subscribable iCal (.ics) feed URL per trip and per inbound program
  • Events include: title, date/time, location, description
  • Feed updates automatically when itinerary/events change

Business rules engine

Payment rules
RULE: Late Fee Assessment WHEN payment.status = 'overdue' AND days_since_due > trip.late_fee_grace_days AND late_fee_not_already_assessed_this_cycle THEN create_charge(trip.late_fee_amount) AND send_email('late_fee_notification', student, parent) RULE: Auto-Cancellation WHEN payment.status = 'overdue' AND days_since_due > trip.auto_cancel_after_days THEN cancel_subscription() AND update_registration(status='cancelled', reason='non_payment') AND send_email('auto_cancellation', student, parent, teacher) AND notify_admin('auto_cancellation', registration) RULE: Free Teacher Calculation GIVEN student_count, free_teacher_ratio THEN free_teachers = FLOOR(student_count / free_teacher_ratio) AND paid_positions = total_group_size - free_teachers AND price_per_student = total_trip_cost / paid_positions
Notification rules
RULE: Task Deadline Approaching WHEN task.deadline - today <= configurable_days (default: 7) AND task.status = 'incomplete' THEN send_email('task_reminder', student, parent) RULE: Task Overdue WHEN today > task.deadline AND task.status = 'incomplete' THEN update_task(status='overdue') AND send_email('task_overdue', student, parent) AND repeat_every(configurable_days, default: 3) RULE: New Host Family Interest WHEN interest_form.submitted THEN notify_local_coordinator(interest_form.city) AND send_email('interest_confirmation', host_family) AND send_email('continue_application_link', host_family, delay: 24h)
Vetting rules
RULE: Vetting Complete WHEN all_required_steps_completed(host_family) AND all_steps_passed THEN update_vetting_status('approved') AND notify_admin('family_approved', host_family) AND send_email('approved_notification', host_family) RULE: Background Check Flagged WHEN background_check.status = 'flagged' THEN notify_admin('background_flagged', host_family) AND pause_vetting_workflow(host_family)

PDF generation

Trigger: Admin clicks "Generate Profile" on approved host family.

Data sources: HostFamilyInterest (contact info) + HostFamilyApplication (household details) + HostFamilyProfile (photos, letter, interests, schedule).

  • Branded header (LNL logo, program name)
  • Family photo(s) prominently displayed
  • Structured sections: Family Overview, Home Details, Interests & Activities, Daily Schedule, Welcome Letter
  • Professional formatting suitable for sending to international partners
  • Admin can preview before finalizing
  • Implementation: HTML → PDF conversion (most flexible approach)
07 —

Migration considerations

Data export requirements
  • From Youli: all active trip data (registrations, payment history, task completions), traveler/parent/teacher accounts, itinerary library
  • From Google Sheets: all inbound program spreadsheets (per-city vetting sheets), map columns to HostFamily/InboundStudent/VettingRecord entities
  • Handle: inconsistent data formats, missing fields, duplicate entries
  • Validate: no data loss during migration (reconcile record counts)
Transition plan
  • Parallel operation period (1-2 months): run new platform alongside Youli for one trip cycle
  • Staff training: all 8 team members trained before cutover
  • Cutover timing: align with natural business cycle (between trip seasons, not mid-registration)
  • Rollback plan: maintain Youli access for 30 days post-cutover
08 —

Non-functional requirements

Performance

Page load < 2s. API response < 500ms. Support 200 concurrent users (peak registration). File upload up to 50MB (videos, photos).

Security

HTTPS everywhere (TLS 1.2+). Input validation/sanitization. PCI compliant (Stripe handles all card data). Regular automated backups. GDPR: ability to export/delete user data.

Availability

99.5% uptime target (~44 hours downtime/year). Scheduled maintenance communicated in advance. Automated health monitoring and alerting.

Scalability

Current: ~8 admins, ~500-1000 travelers/year, ~200-400 host families/year. Design for 10x growth without architectural changes. Index on: user_id, trip_id, program_id, city, status, dates.

Appendix — Recommended approaches

This section provides guidance for evaluating implementation proposals. It is not prescriptive — the core specification can be implemented on any modern web stack.

Option 1: Modern web framework (custom build)

Example stack: Next.js/React (frontend) + Node.js or Python (backend) + PostgreSQL (database) + Vercel/Railway/AWS (hosting)

Evaluation criteria when reviewing proposals

Domain understanding

Do they understand travel/education/multi-user portals? Ask for relevant portfolio examples.

Maintenance story

Who fixes bugs after launch? What's the hourly rate for changes? Is there a support contract?

Incremental delivery

Insist on milestone-based delivery. Bi-weekly demos minimum. Never "we'll show you everything at the end."

Code ownership

Do you own the code? Can another developer pick it up? Avoid proprietary platforms where the builder holds the keys.

Scope change process

Things will change during build. What's the process for adding/modifying requirements without blowing up the budget?

References

Ask for 2-3 past clients you can contact. Specifically ask those clients about post-launch support quality.
